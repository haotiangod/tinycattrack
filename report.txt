============================================================
  TinyCat 模组 - 问题报告 (2026-06-25)
============================================================

一、代码结构问题
--------------------

1. resource/ 目录冗余（高优先级）
   - resource/sts-stat-tracker-master/ 包含完整的原始 StatsTracker 项目副本
     （Go 后端、Python 脚本、runs/ 数据、steam/ 配置等），大量文件与当前模组无关
   - 建议：如果仅作为参考，可保留 Git 历史后删除；或移至独立的 reference/ 目录
   - 影响：增加仓库体积，IDE 索引变慢，混淆新贡献者

2. build/ 和 bin/ 目录未加入 .gitignore
   - 构建产物（.class 文件、JAR 包）不应提交到版本控制
   - 建议：在 .gitignore 中添加 build/ 和 bin/

3. SaveAndContinuePatch 已废弃但未删除
   - 整类注释掉，功能已标记为"移至外部工具实现"
   - 建议：如果确认不再需要，应完全删除而不是注释保留

4. 名称映射表重复维护
   - Utils.CARD_NAME_REPLACEMENTS 和 Card.nameReplacementMap 包含几乎相同的映射
   - 建议：统一到一处维护，另一处引用

5. 多个 Python 脚本散落
   - 根目录：format_json.py
   - resource/ 内：analyze_runs.py, clean_duplicates.py, clean_mapping.py,
     convert_mapping.py, extract_names_from_runs.py 等 10+ 个脚本
   - 建议：统一整理到 scripts/ 目录，添加 README 说明用途

二、代码质量问题
--------------------

6. 硬编码黑名单维护成本高（中优先级）
   - Run.java 中大量硬编码列表：
     bannedCards, bannedRelics, bannedNeows, bannedBossRelics,
     bannedEnemies, bannedAct1Encounters, bannedAct2Encounters 等
   - 问题：每次游戏更新或发现新 Mod 卡牌都需要手动修改代码
   - 建议：考虑将黑名单移至外部 JSON 配置文件

7. 金币估算公式依赖硬编码常数
   - parseGold() 中的 getNeowBonusDeduction() 有 15+ 个硬编码扣除常数
   - 这些常数是通过 RMSE 最小化得出，但缺少来源说明和验证方法
   - 建议：添加数据来源注释，说明常数是如何计算得出的

8. 第0层HP估算硬编码
   - Ironclad 的 Burning Blood 回血 6 为硬编码
   - 若游戏未来更新改变回血数值，估算法将失效
   - 建议：通过反射读取 Burning Blood 的实际数值，或添加常量配置

9. 缺少单元测试
   - 整个项目没有任何 JUnit 或其他测试框架的测试
   - 核心计算逻辑（金币估算、第0层HP估算、连胜计算）缺乏验证
   - 建议：至少为核心算法添加单元测试

10. Mod 卡牌检测仅靠 contains(":")
    - Run.valid() 中识别 Mod 卡牌/遗物仅检查名称是否包含 ":"
    - 可能漏判（如名称中不含冒号的 Mod 内容）或误判（如特殊情况下）
    - 建议：这是一个已知的实用主义决策，但应在注释中明确说明局限性

三、设计问题
--------------------

11. Localization 初始化顺序问题
    - Localization.initialize() 在 tinycat.initialize() 中调用
    - 此时 Settings.language 可能为 null，导致先加载英文再在 get() 时重载
    - MoreStatsScreen 中 getClasses()/getStatTypes() 使用懒加载绕过此问题
    - 建议：文档化初始化顺序依赖，避免未来修改时引入回归

12. 金币数据来源的双路径
    - 优先读取 gold-tracker 模组输出文件（精确）
    - 回退到 gold_per_floor 公式估算（近似）
    - 问题：如果用户没有安装 gold-tracker 模组，所有对局都使用估算值
    - 建议：在 UI 中标注数据来源（精确/估算），让用户了解数据质量

13. 统计逻辑分散在多个类中
    - ClassStat.StatCollector 内部类承担了绝大多数聚合逻辑（~800行）
    - 删牌统计、火堆统计、商店统计等逻辑全部内联在 StatCollector 中
    - 建议：考虑将各维度统计拆分为独立的 Collector 类

四、文档问题
--------------------

14. CHANGELOG 缺失
    - 根目录没有 CHANGELOG.md，版本变更记录仅在 README 末尾
    - 建议：创建独立的 CHANGELOG.md，README 中仅保留最近版本

15. 构建说明不完整
    - build-local.bat 存在但缺少 Linux/Mac 构建脚本
    - build.gradle.kts.example 存在但用途不明确
    - 建议：统一构建文档，说明两个 gradle 文件的区别

16. 映射文件格式说明缺失
    - chinese_english_mapping.json 的格式（双向自动检测）在代码中有注释
    - 但缺少独立的格式说明文档，协作者不清楚如何添加新映射
    - 建议：在 NAME_MAPPING.md 或 README 中补充格式说明

五、兼容性风险
--------------------

17. 依赖 RunHistoryPlus 的扩展字段
    - RunData 中多个字段（neow_bonus_log, potion_use_per_floor,
      shop_contents, improvable_cards 等）来自 RunHistoryPlus 扩展
    - 如果 RunHistoryPlus 更新导致字段名变更或数据格式变化，需要同步修改
    - 建议：在 README 中明确依赖的 RunHistoryPlus 最低版本

18. 游戏版本兼容性
    - 卡牌名称映射表（nameReplacementMap）处理了游戏早期版本到当前版本的变更
    - 但无法保证未来版本不会引入新的名称变更
    - 建议：建立名称映射的更新机制文档

============================================================
  总结
============================================================

整体评价：代码结构清晰，核心统计逻辑正确，注释完善度高。
主要改进方向：
  1. 清理冗余文件（resource/、build/、bin/）
  2. 补充单元测试覆盖核心算法
  3. 将硬编码配置外置化（黑名单、金币常数）
  4. 统一名称映射表维护
  5. 完善构建和贡献文档

当前版本 (v4.0.9) 稳定可用，以上问题不影响正常使用。
